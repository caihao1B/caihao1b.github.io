# 第三个项目的展示与面试讲解说明

第三个项目页是 `ros2.html`，主题为“ROS 2 在线覆盖导航与六轴机械臂作业扩展”。页面把硕士论文的导航研究和上传的移动搬运工程放在同一条技术发展线上：先说明机器人如何持续执行覆盖任务，再展示停靠后怎样执行机械臂作业。

论文和搬运工程是两份不同的实现材料。论文中的实验结果属于在线覆盖导航；机械臂属于后续移动操作扩展。这个区分能让介绍更具体，也能避免在面试中把不同阶段的结果混在一起。

## 一 如何打开和使用

解压网站后打开 `index.html`，进入第三个项目“ROS 2 与机械臂”；也可以直接打开 `ros2.html`。本页使用本地 JavaScript、Canvas 和视频文件，核心内容无需联网。

如果浏览器限制本地视频或脚本，可以在网站根目录启动一个本地 HTTP 服务，再打开该地址：

```bash
python3 -m http.server 8000
```

Windows 如果没有 `python3` 命令，可使用已安装的 Python 启动器：

```powershell
py -m http.server 8000
```

浏览器访问 `http://localhost:8000/ros2.html`。这是网站预览，不会启动 ROS 2 或控制机器人。

正式展示前，把页面打开一次，确认机械臂视图出现、视频能够播放。建议浏览器缩放为 100%，机械臂播放速度先保持 1×；需要解释关节时再暂停或切换 0.5×。

### 开场可以这样说

“我的三个项目分别关注覆盖路径规划、农田任务调度和机器人在线执行。这个页面主要介绍我的 ROS 2 在线覆盖导航论文，同时展示一个移动操作扩展工程。论文解决动态障碍出现后怎样恢复覆盖任务；扩展工程把底盘导航和六轴机械臂抓放连接起来。机械臂交互视图根据项目源码重建，旁边的 Gazebo 录像用于展示实际运行过程。”

### 论文部分的核心讲法

“离线计划给出分段路径，在线执行器把它转换为滚动窗口。局部障碍出现后，不同层次分别负责等待、让行、局部重接和区域结构修复。更关键的是，被绕过或跳过的部分需要显式记录，不能因为机器人又开始移动，就认为覆盖任务已经完成。”

点击 C1 时指出“绕行后接回当前段”，点击 C2 时指出“保持顺序进入下一段”。D1 调整剩余段序，D2 可以替换局部剩余覆盖几何；它们受准入条件约束，页面层级不表示每次都必须依次尝试。

如果需要讲实验指标，称为“论文报告的参考工作区域实现率”。页面的 `η_ref` 是实际扫掠区域与同地图名义参考区域的重叠比例，不是整张地图的自由空间覆盖率。表中每组聚合三个地图类别的均值，展示均值与标准差。本次制作网站没有重新运行论文实验。

## 三 机械臂没有近景录屏时怎样展示

现有解决办法是把三类材料结合起来：可检查的源码模型、可交互的运动学视图、保留真实事件的 Gazebo 录屏。

| 材料 | 可以说明什么 | 不能单独说明什么 |
| --- | --- | --- |
| Xacro、控制器配置、抓放执行器 | 六轴结构、关节轴与限位、控制接口、预设动作、服务调用顺序。 | 不能单凭文件存在证明整套系统已稳定运行。 |
| 浏览器机械臂工作台 | 这些关节参数如何改变模型位姿；预设之间的动作关系；末端坐标的正运动学计算。 | 不是 Gazebo 物理仿真、ROS 运行回放、无碰撞规划或实际夹持验证。 |
| 上传的 Gazebo 录屏 | 场景中的底盘移动、任务阶段、终端日志、该次运行的终止情况。 | 全景中的机械臂较小，不能逐关节确认动作，也不能证明所有物体最终放置正确。 |

### 机械臂面板的推荐操作

1. 先选择 `pick_hover`，打开“关节坐标轴”，轻微拖动视图，让面试官看清六个关节。
2. 再选择 `pick_contact` 和 `carry`，说明这些目标角来自 `competition_scene.json`。
3. 在 `pick_hover` 附近小幅调整 J2，观察连杆和末端坐标变化；必要时再调 J1 解释底座回转。
4. 点击“播放动作”，在“附着与携带”和“打开与解除”附近暂停，讲解 `FollowJointTrajectory` 与附着服务的区别。
5. 最后点击源码链接，展示原始路径、行号和动作参数，说明模型与接口有对应实现。

面板显示的末端点是 `grasping_frame` 原点，相对 `base_footprint` 计算。原 Xacro 把该坐标系设在 `link6` 原点，不是两指之间的工具中心。尤其 J6 绕这个原点旋转时，朝向可以改变而该点的 XYZ 不变，这是模型坐标系定义的结果。

### 可以直接使用的机械臂讲解

“这里使用项目原有的自定义 six_arm 六轴模型。我把机械臂关节控制纳入移动搬运任务流程：先导航到取物服务位，再通过 FollowJointTrajectory 发送预设关节目标，随后请求 Gazebo 的连杆附着服务，进入携带姿态并继续导航。释放后还要检查物体在仿真中的位置，才能判断放置结果。”

“网页中的运动来自原模型参数和预设角度的正运动学插值。它用于解释结构和控制流程，不代替物理仿真。真正运行中的动作结果需要看控制器反馈、物体位姿和任务日志。”

以上表述中的个人职责，应与自己实际完成并能解释的工作保持一致；底层 ROS 2 框架和原机器人模型不需要说成个人从零开发。

## 四 抓取与放置的实际顺序

源码依据是 `tools_demo/tools_demo/grasp_executor.py` 的 `pick_model()` 与 `place_model()`。以下是上传 2026-06-04 快照的默认配置路径。

### 抓取

1. 读取目标模型位姿，检查配置可达距离和抓取前真值条件。
2. 发送夹爪 `open` 目标。
3. 执行 `pick_hover`，再执行 `pick_contact`。
4. 请求 `/ATTACHLINK`，把目标模型的 `link` 与机器人 `link6` 建立仿真附着关系。
5. 发送夹爪 `closed` 目标。
6. 执行 `carry`。
7. 检查被搬运物体与机器人距离、物体高度等真值条件。

`pick_model()` 本身不以一个 `home` 动作为起点。网页可以为演示加入初始复位，但它属于演示编排，不能解释成该函数中的额外命令。

### 放置

1. 执行 `place_hover`，再执行 `place_release`；J1 可以叠加配置中的放置槽位偏置。
2. 发送夹爪 `open` 目标。
3. 在默认 `guarded` 模式下等待 0.35 秒，然后请求 `/DETACHLINK`。
4. 默认等待 1.25 秒，再依次收回到 `place_hover`、`carry`；默认启用回到 `home`。
5. 按配置再次等待稳定，然后检查目标物体的区域归属与高度。
6. 任务控制器随后按配置处理退出导航、局部修正、退离与后续任务。

浏览器时间轴用于讲解，省略或归并的服务等待不代表实际运行速度。源码中直接速度退离 `post_place_retreat_enabled` 默认关闭，退出导航 `post_place_exit_enabled` 默认开启，两者也不能混为同一个动作。

## 五 面试中怎样解释通信层次

| 层次 | 工程接口 | 推荐讲法 |
| --- | --- | --- |
| 任务解析与调度 | Python 任务对象、阶段状态与进度 Topic | 输入先形成可校验的颜色、数量和目标区域，再生成逐件搬运任务。 |
| 任务控制到导航 | `NavigateToPose` Action | 导航是持续执行的目标，有结果、反馈与取消语义。 |
| 抓放执行到关节控制 | `FollowJointTrajectory` Action | 发送六轴或夹爪的关节目标和到达时间，检查执行返回与控制器状态。 |
| 抓放执行到 Gazebo 插件 | `/ATTACHLINK`、`/DETACHLINK` Service | 请求建立或解除仿真连杆关联。 |
| Gazebo 到结果核验 | `/competition/model_states` Topic | 周期获取物体在仿真中的位置，审计任务记录与物理状态是否一致。 |
| 任务控制到观察界面 | `/competition/status`、`/competition/progress` 等 Topic | Foxglove 等界面用于观察阶段、对象与进度，不能替代结果审计。 |

搬运工程顶层是 Python 的任务阶段流程，可按 FSM 解释。Nav2 内部存在 BT Navigator。论文中的覆盖监督结构属于另一份研究材料，不能把两者说成同一套顶层行为树实现。

搬运源码的导航配置是 AMCL、NavFn 的 Dijkstra 模式和 DWB 控制器。论文动态干扰场景主要使用 MPPI，同时保留 Regulated Pure Pursuit 作为几何稳定跟踪参考。说清“哪个项目、哪个配置”比只列算法名字更有说服力。

## 六 简历中可使用的表述

建议在一个项目条目里分清“论文研究”和“工程扩展”，或者在简历空间允许时拆为两个条目。下面的内容强调实际技术对象，没有把网页演示当成机器人实验结果。

### 在线覆盖导航论文

**ROS 2 在线覆盖导航与动态干扰恢复研究**

- 基于 ROS 2、Nav2 与 Gazebo 构建分段覆盖任务的在线执行框架，衔接滚动路径窗口、障碍物预测和分层任务监督。
- 设计等待、让行、同段重接、有序跨段重接与局部结构修复机制，并显式记录跳过段、清理任务及残余关闭结果。
- 结合任务日志与覆盖指标分析动态干扰下的执行表现，区分任务正常终止、参考区域实现率和剩余作业责任。

### 移动操作扩展

**ROS 2 移动搬运与六轴机械臂仿真集成**

- 基于现有机器人模型与 ROS 2 组件，集成移动底盘、six_arm 六轴机械臂、Nav2 导航及任务阶段调度，组织逐件取物、搬运、放置和退出流程。
- 通过 ros2_control 与 FollowJointTrajectory 调度机械臂预设姿态及夹爪目标，结合 Gazebo LinkAttacher 建立仿真抓放链路。
- 利用 Gazebo 模型真值与结构化日志核验放置区域、物体高度及后续位移，分析导航失败与多物体放置干扰。

如果个人职责只覆盖其中一部分，应把相应动词调整为“参与集成”“负责某模块”或“复现并扩展”。不要为了覆盖机械臂关键词，把规划中的 xArm6、视觉抓取或 MoveIt 在线规划写成该项目既有成果。

### 面试常见追问

**“没有机械臂近景录像，怎样证明你做过？”**

可以打开 URDF、控制器配置和抓放函数，逐一解释关节、动作接口和调用顺序，再展示原始运行视频中的对应阶段。浏览器模型用于使结构更易检查；对于录像不能证明的夹持细节，说明准备补充控制器反馈与物体位姿记录。

**“这是否使用 MoveIt 做自主抓取规划？”**

当前主链使用配置预设和关节轨迹控制。上传工程包含 MoveIt/KDL 配置，但在线 IK、碰撞规划和自主抓取没有在这条主链中闭环。后续可在保留任务调度与控制器接口的基础上，把预设轨迹替换成规划结果。

**“目标是摄像头识别出来的吗？”**

当前搬运链主要使用 Gazebo 模型真值和模型名称前缀选取红蓝目标。相机消息用于显示与截图材料；它不是已经完成的视觉识别或视觉伺服闭环。

**“为什么录像里出现失败？”**

约 05:59 的终端日志显示导航看门狗因 `odom_pose_unstable` 停止动作。它说明该次任务在导航稳定性检查处终止。关闭进程时出现的 `rclpy InvalidHandle` 属于之后的关闭阶段，应分别定位。保留失败过程可以具体讨论保护逻辑和故障归因。

**“状态显示 success 是否就算完成？”**

还要检查物体最终是否留在目标区。当前源码虽然记录 final audit，但 `all_truth_ok=false` 没有自动把 `_succeed()` 改为失败。后续应把最终真值审计纳入完成判定，并在释放前后检查已完成物体是否被移动。

## 八 已知配置差异和下一步验证

### 夹爪参数

源配置给出 `open=0.20 m`、`closed=0`，但 `finger_joint1` 的 URDF 行程是 `0–0.06 m`。网页对可视几何做限幅，并保留原始请求值。原关节的正向运动还需要与实际开合语义核对：配置状态名本身不能证明两指间距符合预期。

这里没有修改机器人源码，也没有确认控制器会怎样处理原始超限目标。下一次运行应先核对关节方向、URDF 限位和夹爪命令，再做可重复的开合测试。

### 机械臂控制接口范围

`arm_gazebo.xacro` 的通用 position 接口参数写有 `min=-1`、`max=1`，而部分预设目标含 `1.17` 和 `1.2 rad`。这些接口参数与 URDF 角度限位并不是同一组值，需要在原 ROS 2/Gazebo 环境检查控制器实际处理方式及执行反馈。网页仅按模型关节限位显示，不代表完成了运行端限位校验。

### 抓放物理与最终审计

LinkAttacher 是仿真附着机制，不是已验证的摩擦夹持或力闭合。后续验证应关注：抓取前物体是否与末端对齐；附着后物体是否跟随；解除后是否留在目标区；机械臂和底盘后续动作是否推走已放置对象。

## 九 后续补录的具体办法

不必一次录一段复杂的全流程视频。优先录一段 60–90 秒的单物体抓放近景，再录一段底盘转场片段，最后用任务日志和审计结果串起来。

### 录制画面安排

1. 在 Gazebo 中将视角对准机械臂和目标物体，保持末端与地面可见。
2. 旁边放一个窄终端窗口，显示当前任务阶段或关节控制器反馈。
3. 先录空载 `home`、`pick_hover`、`pick_contact`、`carry` 等姿态，以确认关节目标确实被执行。
4. 再录单个物体的附着、携带、解除、机械臂收回和放置后稳定过程。
5. 最后记录最终物体位姿与审计结果；如果发生失败，保留现场并说明原因。

正式录制前，先在已经能正常启动的 ROS 2 Humble 工作空间中检查接口。以下为观察命令，不会发布运动命令：

```bash
ros2 action list -t
ros2 topic list -t
ros2 topic echo /joint_states --once
ros2 topic echo /arm_controller/controller_state --once
ros2 topic echo /gripper_controller/controller_state --once
ros2 topic echo /competition/model_states --once
```

如需补充可重放的数据证据，可在任务开始前启动一个新 rosbag 输出目录：

```bash
ros2 bag record -o robot_evidence_take01 \
  /joint_states \
  /arm_controller/controller_state \
  /gripper_controller/controller_state \
  /competition/model_states \
  /competition/status \
  /competition/progress \
  /tf /tf_static /clock
```

先确认输出目录不存在；再次录制时改为 `robot_evidence_take02` 等新名称。录制结束按 `Ctrl+C`，保留目录和本次 `run_artifacts`。这些 Topic 应以当前实际 `ros2 topic list -t` 为准；如果部署版本改了名称，先核对再调整。

记录关节和 Topic 数据不会自动记录所有 Action 或 Service 的请求与返回。因此还应保留控制器输出、`manipulation.jsonl`、`completed_object_audit.jsonl` 以及 `summary.json`，并记录本次使用的源码版本和场景配置。
